## Abstract

The AI-Based Virtual Risk and Compliance Intelligence System, internally designated as Digital Twin AI, is a full-stack web application designed to construct an isolated, per-user digital twin. By synthesizing data from three distinct but interconnected life domains—personal finance, academic performance, and habit/wellbeing consistency—the system provides a unified intelligence platform. 

Current personal tracking tools operate in silos, failing to capture the cross-domain ripple effects of human decision-making, such as the impact of sleep deprivation on academic retention, or financial anxiety on habit adherence. This project addresses this fragmentation through machine learning forecasting (using Ridge Regression, Random Forest, and Calibrated Logistic Regression), stochastic Monte Carlo counterfactual simulation capable of executing up to 15,000 vectorized iterations, deterministic rule-based recommendations, and an autonomous tool-calling AI conversational agent.

Built with Next.js 14, FastAPI, PostgreSQL, and orchestrated via Docker Compose, the system ensures data privacy through GDPR/CCPA compliance, JWT authentication, and strict tenant isolation. The project successfully demonstrates that cross-domain synthesis yields highly actionable insights that single-domain applications cannot provide.

# Chapter 1 — Introduction

## 1.1 Project Overview

The **AI-Based Virtual Risk and Compliance Intelligence System** (internally designated **Digital Twin AI**) is a full-stack web application that constructs an isolated, per-user digital twin by synthesizing data from three interconnected life domains: **personal finance**, **academic performance**, and **habit and wellbeing consistency**. The system unifies these traditionally siloed tracking disciplines into a single intelligence platform powered by machine learning forecasting, stochastic Monte Carlo counterfactual simulation, deterministic rule-based recommendations, and an autonomous tool-calling AI conversational agent.

The fundamental thesis underlying this project is that human life operates as an interconnected system wherein decisions in one domain carry immediate ripple effects across others. For example, cutting sleep to study late leads to cognitive burnout, falling examination scores, increased stress, and erratic expenses. Existing personal tracking tools—banking apps, study trackers, and health loggers—monitor their respective domains in isolation, failing to capture these cross-domain dynamics.

This project addresses that fragmentation by constructing a unified predictive digital twin for each user.

## 1.2 Problem Statement

Modern personal tracking tools remain fundamentally siloed:

- **Banking and budgeting applications** monitor historical cash flow but ignore academic demands or sleep deprivation that trigger impulse spending.
- **Study trackers and LMS tools** measure examination performance in isolation from financial anxiety and recovery metrics.
- **Habit and health trackers** log sleep and workouts without connecting them to cognitive bandwidth or long-term financial runway.

Because human decision-making is inherently cross-domain, a dedicated system is required that:

1. Ingests and unifies daily finance transactions, study sessions, and wellbeing logs.
2. Generates ML-driven forward projections with cold-start dynamic blending and explicit data provenance.
3. Runs stochastic Monte Carlo counterfactual simulations coupling cross-domain dynamics.
4. Generates grounded, explainable rule-based recommendations citing authentic user metrics.
5. Provides an interactive conversational AI assistant with server-side security injection and grounded tool execution.

## 1.3 Objectives

1. To design and implement a tri-domain digital twin platform that synthesizes personal finance, academic focus, and habit consistency into a unified predictive model.
2. To develop and deploy three trained machine learning models (Ridge Regression, Random Forest Regressor, Calibrated Logistic Regression) for domain-specific forecasting.
3. To implement a vectorized Monte Carlo simulation engine capable of 500 to 15,000 stochastic iterations with explicit cross-domain coupling heuristics.
4. To build a deterministic, rule-based recommendation engine that cites authentic user metrics against clinical and financial thresholds.
5. To create an autonomous AI conversational assistant with seven server-side tools, multi-provider fallback, and anti-spoofing context injection.
6. To ensure privacy compliance through GDPR/CCPA data portability export and cascade account deletion.
7. To containerize the complete application using Docker Compose for reproducible deployment.

## 1.4 Scope

The project encompasses:

- **Frontend:** Next.js 14 (App Router) with React 18, TypeScript, Tailwind CSS, and Recharts for data visualization.
- **Backend:** Python 3.11+ with FastAPI, SQLAlchemy 2.0 (async), Pydantic v2 validation, and JWT-based authentication.
- **Machine Learning:** scikit-learn pipeline with three trained models and cold-start blending.
- **Simulation:** NumPy-based vectorized Monte Carlo engine with parametric and bootstrap shock models.
- **AI Agent:** Google Gemini primary, OpenAI-compatible secondary, deterministic offline tertiary fallback chain.
- **Database:** PostgreSQL 16 (production), SQLite via aiosqlite (testing/CI).
- **Deployment:** Docker Compose orchestration with three services.

## 1.5 Significance

This project contributes to the field of personal informatics by demonstrating that cross-domain synthesis—connecting financial behavior, academic performance, and wellbeing metrics—yields actionable insights that isolated domain trackers cannot provide. The Monte Carlo simulation engine enables counterfactual "what-if" analysis that empowers users to understand the stochastic consequences of life decisions before committing to them.

# Chapter 3 — System Design

## 3.1 Architectural Overview

The system follows a **three-tier layered architecture** with clear separation of concerns:

1. **Presentation Layer (Frontend):** Next.js 14 App Router with React 18, TypeScript, and Tailwind CSS. Communicates with the backend exclusively through REST API calls with JWT bearer tokens.

2. **Application Layer (Backend):** FastAPI (Python 3.11+) providing RESTful API endpoints, business logic services, ML model inference, simulation execution, recommendation generation, and LLM-powered chat orchestration.

3. **Persistence Layer (Database):** PostgreSQL 16 in production (via Docker) and SQLite via aiosqlite for testing and CI environments. SQLAlchemy 2.0 async ORM abstracts database interactions.

## 3.3 Data Flow Summary

1. **User logs data** via collapsible quick-entry panels (Finance, Study, Habits) on the frontend.
2. **Frontend sends** validated JSON payloads to FastAPI REST endpoints with JWT bearer token.
3. **Backend validates** the JWT, extracts `user_id` from token claims, and enforces row-level tenant isolation.
4. **Data is persisted** to PostgreSQL via SQLAlchemy async ORM with composite indexes on `(user_id, date)`.
5. **Dashboard aggregates** KPIs from persisted data, computes the Life Path Index, and invokes ML models for forecasting.
6. **Simulation engine** reads baseline state from user data, generates stochastic shocks, and runs vectorized Monte Carlo iterations.
7. **Recommendation engine** evaluates user metrics against centralized thresholds and generates grounded actionable items.
8. **AI chatbot** receives user messages, orchestrates tool calls server-side, and returns responses with chart specifications.

## 6.3 Indexing Strategy

The database employs the following indexing strategies for query performance optimization:

1. **Primary Key Indexes:** Auto-created on `id` column for all tables.
2. **Email Index:** Unique index on `users.email` for login lookup performance.
3. **Foreign Key Indexes:** `user_id` indexed on all child tables for tenant-scoped queries.
4. **Composite Indexes:** `(user_id, date)` composite indexes on `finance_entries`, `study_sessions`, `habit_logs`, and `twin_snapshots` for efficient date-range filtered queries scoped to individual users.
5. **Temporal Index:** `login_events.created_at` indexed for audit trail chronological queries.

## 6.4 Cross-Platform UUID Type

A custom `GUID` TypeDecorator class (`app/models/user.py`) ensures UUID compatibility across PostgreSQL (native UUID type) and SQLite (stored as `CHAR(36)` strings). This allows the same ORM models to function in production PostgreSQL and CI/testing SQLite environments without code changes.

# Chapter 7 — Authentication and User Management

## 7.1 Authentication Architecture

The system implements a stateless JWT-based authentication mechanism with the following components:

### 7.1.1 Password Hashing

Passwords are hashed using **bcrypt** with per-user random salt generation:

```python
def get_password_hash(password: str) -> str:
    salt = bcrypt.gensalt()
    return bcrypt.hashpw(password.encode("utf-8"), salt).decode("utf-8")
```

Password verification uses constant-time comparison via `bcrypt.checkpw()` to prevent timing attacks.

**Implementation file:** [`backend/app/core/security.py`](file:///d:/AI-Based-Virtual-Risk-and-Compliance/backend/app/core/security.py)

### 7.1.2 JWT Token Management

- **Token Creation:** JWT tokens are created with the `PyJWT` library, encoding the user's UUID as the `sub` (subject) claim, along with `exp` (expiration) and `iat` (issued at) timestamps.
- **Token Expiration:** Configurable via `ACCESS_TOKEN_EXPIRE_MINUTES` environment variable (default: 1440 minutes = 24 hours).
- **Algorithm:** HS256 (HMAC-SHA256) with a configurable secret key (`JWT_SECRET`).
- **Token Validation:** Every protected endpoint calls `get_current_user()` dependency, which decodes the JWT, extracts the `user_id`, and queries the database to verify the user exists.

**Implementation file:** [`backend/app/api/deps.py`](file:///d:/AI-Based-Virtual-Risk-and-Compliance/backend/app/api/deps.py)

### 7.1.3 Authentication Endpoints

| Endpoint | Method | Description |
|:---|:---|:---|
| `/api/v1/auth/register` | POST | Creates a new user account with email and hashed password, creates associated profile |
| `/api/v1/auth/login` | POST | Validates credentials, generates JWT token, logs login event |
| `/api/v1/auth/demo-login` | POST | One-click demo authentication (enabled via `ENABLE_DEMO_LOGIN` flag) |

### 7.1.5 Login Event Auditing

Every authentication attempt (successful or failed) is recorded in the `login_events` table, capturing:
- Timestamp of the attempt
- Success/failure status
- Authentication method (`password` or `demo-login`)
- Client browser/OS from the User-Agent header
- Client IP address

This provides a complete audit trail accessible through the History page under the "Login History" tab.

## 7.2 Rate Limiting

The system implements an in-memory **sliding window rate limiter** to prevent brute-force authentication attacks:

```python
class InMemoryRateLimiter:
    def is_allowed(self, key: str, max_requests: int, window_seconds: int = 60) -> Tuple[bool, int]:
```

- Rate limit key is constructed as `{endpoint_prefix}:{client_ip}`.
- Expired timestamps outside the sliding window are automatically purged.
- When the limit is exceeded, the system returns `HTTP 429 Too Many Requests` with a `Retry-After` header indicating the wait duration.
- Thread-safe implementation using `threading.Lock`.

**Implementation file:** [`backend/app/core/security.py`](file:///d:/AI-Based-Virtual-Risk-and-Compliance/backend/app/core/security.py)

## 8.4 Cold-Start Dynamic Blending

A critical innovation in this system is the **cold-start dynamic blending** mechanism that handles the transition between global model predictions and personalized predictions:

```
personal_weight = min(1.0, user_data_points / 30.0)
```

- **0 data points (personal_weight = 0.0):** Pure global model prediction → data source labeled as `"global"`
- **1–29 data points (0 < personal_weight < 1.0):** Blended prediction → labeled as `"blended"` with percentage breakdown
- **30+ data points (personal_weight = 1.0):** Fully personalized prediction → labeled as `"personal"`

Each prediction response includes an explicit `data_source` badge and `explanation` text describing the blending ratio, providing full transparency to the user about prediction provenance.

# Chapter 10 — Forecasting

## 10.1 Forecasting Architecture

The forecasting subsystem extends the ML models described in Section 9 by projecting predictions forward in time with expanding uncertainty bounds. Forecasts are generated on-demand when the user navigates to the respective domain prediction pages or when the AI chatbot invokes the `run_prediction` tool.

## 10.2 Finance Forecasting

### 10.2.1 Projection Mechanism

The finance forecasting engine projects monthly expenses and savings over a 1-to-6-month horizon:

1. **Personal Trend:** Monthly expenses grow at 1% per month: `personal_exp_m = base × (1.0 + 0.01 × m)`
2. **Global Trend:** Ridge model prediction with seasonal sinusoidal modulation: `global_exp_m = prediction × (1.0 + 0.015 × sin(m × π/6))`
3. **Blended Forecast:** `blended = (1 − w_personal) × global + w_personal × personal`
4. **Confidence Bounds:** Expand with √(1 + m/6) horizon scaling factor

### 10.2.2 Output Structure

Each monthly forecast point includes:
- Projected expenses: lower, expected, upper (80% confidence interval)
- Projected savings: lower, expected, upper
- Cumulative savings: running total with bounds
- Projected date (YYYY-MM format)

### 10.2.3 Data Source Provenance

Every forecast response carries:
- `data_source`: "global", "blended", or "personal"
- `personal_weight`: 0.0 to 1.0
- `user_data_points`: count of user entries
- `explanation`: natural language description of the blending methodology
- `model_metadata`: algorithm name, training metrics, and source breakdown

## 10.3 Academic Score Forecasting

### 10.3.1 Current Score Prediction

The system predicts the user's expected examination score based on current behavioral patterns (study hours, consistency, sleep, exercise, mood) using the Random Forest model with cold-start blending against historical user scores.

### 10.3.2 Scenario Analysis

## 10.4 Habit and Burnout Forecasting

# Chapter 11 — Simulation Engine

## 11.1 Overview

The simulation engine is the system's most computationally intensive subsystem, implementing a **vectorized Monte Carlo counterfactual simulation** that projects 1 to 12 months into the future across all three domains (finance, study, habits/burnout) simultaneously. The engine is designed to answer "what-if" questions by comparing a baseline trajectory against a user-specified intervention scenario.

**Implementation file:** [`ml/simulator.py`](file:///d:/AI-Based-Virtual-Risk-and-Compliance/ml/simulator.py) (598 lines)

## 11.2 Monte Carlo Methodology

### 11.2.1 Stochastic Iteration Architecture

The simulation executes between 500 and 15,000 stochastic iterations (configurable, default 500). Each iteration represents one possible future realization of the user's life trajectory, with randomized shocks applied to income, expenses, sleep, exercise, study scores, habit consistency, and burnout risk.

### 11.2.2 Shock Generation Models

The engine supports three shock generation modes:

**1. Parametric Model (Default):**
Shocks are drawn from calibrated Gaussian distributions:

| Domain | Mean | Std Dev |
|:---|:---:|:---:|
| Income | 0.0 | 0.02 (2% monthly variance) |
| Expenses | 0.0 | 0.06 (6% monthly variance) |
| Sleep | 0.0 | 0.35 hours |
| Exercise | 0.0 | 6.0 minutes |
| Study Score | 0.0 | 2.2 points |
| Habit Consistency | 0.0 | 0.04 |
| Burnout | 0.0 | 0.04 |

**2. Bootstrap Model (Historical):**
Shocks are generated by 7-day block bootstrap resampling of the user's actual historical data. If any domain has fewer than 20 entries, the system falls back to pooled global residuals for that domain and flags `limited_history = True`.

**3. Compare Mode:**
Runs both parametric and bootstrap models side-by-side, comparing their P50 projections and flagging when they diverge by more than 15%.

### 11.2.3 Vectorized Execution

The simulation is fully vectorized using NumPy arrays of shape `(iterations, horizon)`, avoiding Python loops over iterations. This enables 15,000 iterations to complete in approximately **0.08 seconds** (parametric) or **0.09 seconds** (bootstrap), as verified in the QA report.

## 11.3 Cross-Domain Coupling Heuristics

The simulation engine implements four explicit cross-domain coupling mechanisms, each parameterized via centralized configuration constants in `app/core/simulation_config.py`:

### 11.3.1 Sleep → Study Retention Penalty

```
If sleep_hours < 6.5h:
    retention_penalty = 8% per hour below threshold
    study_score × (1.0 - 0.08 × deficit_hours)
```

**Rationale:** Insufficient sleep (<6.5h) degrades cognitive retention and examination performance.

### 11.3.2 Exercise → Burnout Reduction + Focus Bonus

```
If exercise_minutes >= 30:
    burnout_risk -= 15% (EXERCISE_BURNOUT_REDUCTION = 0.15)
    study_focus_bonus = +6% (EXERCISE_FOCUS_BONUS = 0.06)
```

**Rationale:** Regular physical activity reduces cortisol, prevents chronic nervous system fatigue, and enhances cognitive focus.

### 11.3.3 Financial Runway → Habit Anxiety Penalty

```
If financial_runway < 2.0 months:
    habit_consistency_penalty = 12% × (1 - runway/2.0)
```

**Rationale:** Financial insecurity generates anxiety that degrades routine adherence and wellbeing consistency.

### 11.3.4 Severe Burnout → Study Performance Degradation

```
If burnout_risk > 0.60:
    study_score × (1.0 - BURNOUT_STUDY_PENALTY × (burnout - 0.60) / 0.40)
```

**Rationale:** Severe burnout (>60% risk) causes secondary cognitive performance degradation beyond the direct sleep penalty.

## 14.3 Multi-Provider Fallback Chain

The chatbot implements a resilient multi-provider architecture:

| Priority | Provider | Model | Purpose |
|:---:|:---|:---|:---|
| 1 | Google Gemini | gemini-2.5-flash | Primary LLM for natural language and tool calling |
| 2 | OpenAI-Compatible | Groq / OpenAI / Ollama | Secondary fallback when Gemini quota exhausted or unreachable |
| 3 | Offline Deterministic | Rule-based engine | Tertiary fallback requiring no external API |

### 14.3.1 Provider Selection Logic

1. **Primary provider** is attempted first.
2. On failure (timeout, API error, quota exceeded), the failure is recorded and the next provider is attempted.
3. If all primary providers fail or the 45-second overall deadline is reached, the **offline deterministic provider** is invoked.
4. The offline provider generates structured responses based on tool execution results without LLM text generation.

### 14.3.2 Overall Deadline

A **45-second overall deadline** is enforced across the entire chat turn (including all tool call iterations). This prevents runaway turns from blocking the user interface.

## 14.4 Tool Call Execution Loop

Each chat turn follows a multi-step tool-calling loop with a maximum of **5 tool call iterations**:

1. User message is persisted to `chat_messages` table.
2. Last 10 plain-text messages are fetched as conversation context.
3. System prompt + tool declarations are sent to the LLM provider.
4. If the LLM returns tool calls, each tool is executed server-side with injected user context.
5. Tool results are appended to conversation context and sent back to the LLM.
6. Steps 4–5 repeat until the LLM returns a plain text response (no tool calls) or the 5-iteration cap is reached.
7. The final assistant response is persisted.

## 14.5 Chart Reconciliation System

The chatbot implements an intelligent chart reconciliation system (`reconcile_charts_for_question`) that ensures the visualization attached to the response matches the user's question intent:

| Question Topic | Expected Chart Type |
|:---|:---|
| Study, exam, sleep, academic | `study_vs_sleep` chart |
| Burnout, habit, streak, routine | `habit_burnout_gauge` chart |
| Savings, forecast, runway | `savings_forecast` chart |
| Spending, expenses, breakdown | `expense_donut` chart |

**Key rule:** The expense donut chart is never attached to unrelated answers (e.g., a study question), even if the underlying tool happened to produce financial data.

## 14.6 Disclaimer System

The chatbot conditionally appends a mandatory disclaimer when the conversation involves sensitive topics:

- **Investment topics:** invest, portfolio, stock, crypto, ETF, mutual fund
- **Credit topics:** credit, loan, mortgage, debt consolidation
- **Health topics:** medical, diagnosis, therapy, medication
- **Simulation topics:** simulate, what-if, scenario

The disclaimer states: *"For informational purposes only. Consult a certified financial planner, medical professional, or licensed advisor for personalized advice."*

Duplicate disclaimers are prevented by checking if the response already contains disclaimer markers.

## 14.7 Prompt Injection Resistance

The chatbot has been tested and verified against three categories of prompt injection attacks (as documented in the QA report):

1. **System Prompt Exfiltration:** Attempts to extract the system prompt or API keys are refused.
2. **DAN Safety Override:** Attempts to bypass safety guardrails are rejected.
3. **SQL Injection:** Malicious SQL payloads are neutralized with zero database damage.

# Chapter 19 — Security

## 19.1 Authentication Security

| Mechanism | Implementation |
|:---|:---|
| **Password Hashing** | bcrypt with per-user random salt via `bcrypt.gensalt()` |
| **Token Algorithm** | HS256 (HMAC-SHA256) via PyJWT |
| **Token Expiry** | Configurable (default 24 hours) with `exp` claim |
| **Token Validation** | Every protected endpoint decodes and validates JWT |
| **Credential Error Handling** | Generic error messages ("Invalid email or password") to prevent user enumeration |

## 19.2 Authorization and Tenant Isolation

**Row-level tenant isolation** is enforced across all data endpoints:
- Every database query includes a `WHERE user_id == current_user.id` filter
- `user_id` is extracted from the verified JWT token, never from request parameters
- The AI chatbot's tool executor injects `user_id` server-side, preventing the LLM from accessing other users' data

This design ensures that:
- User A cannot read, modify, or delete User B's data
- The AI assistant cannot be tricked into accessing unauthorized data through prompt injection

## 19.3 Anti-Spoofing in AI Tool Calls

No tool declaration accepts `user_id` as a parameter. The comment in `tools.py` explicitly states:

> *"In accordance with security requirements, NO tool accepts user_id from the model! The backend strictly injects the authenticated user from the verified JWT context."*

This prevents:
- The LLM from fabricating a `user_id` to access other users' data
- Prompt injection attacks that attempt to override the user context

## 19.4 Rate Limiting

The in-memory sliding window rate limiter protects authentication endpoints:
- Key construction: `{endpoint_prefix}:{client_ip}`
- Thread-safe implementation with `threading.Lock`
- Configurable `max_requests` and `window_seconds`
- Returns `HTTP 429 Too Many Requests` with `Retry-After` header when exceeded

## 19.5 CORS Policy

Cross-Origin Resource Sharing is configured via environment variables:
- Only specified origins in `CORS_ORIGINS` are allowed
- Credentials are allowed for JWT cookie handling
- All HTTP methods and headers are permitted for the allowed origins

## 19.6 Data Privacy (GDPR/CCPA)

| Feature | Implementation |
|:---|:---|
| **Data Export** | `GET /api/v1/user/export-data` exports all 11 tables as JSON, explicitly excluding `hashed_password` |
| **Data Deletion** | `DELETE /api/v1/user/delete-data` cascade deletes user account and all associated records |
| **Cascade Relationships** | All ORM relationships use `cascade="all, delete-orphan"` and `ON DELETE CASCADE` foreign keys |
| **Password Exclusion** | Export endpoint explicitly omits password hash from the export payload |

## 19.7 Input Validation

All API inputs are validated through Pydantic v2 schemas:
- Type enforcement (strings, floats, integers, dates)
- Range validation (scores 0–100, mood 1–5, amounts positive)
- Length constraints (descriptions ≤500 chars, email ≤255 chars)
- Required field enforcement
- Invalid input returns `HTTP 422 Unprocessable Entity` with detailed validation errors

# Chapter 20 — Error Handling and Reliability

## 20.1 LLM Provider Resilience

The multi-provider fallback chain ensures the AI chatbot remains functional even when external LLM APIs are unavailable:

1. **Primary (Gemini):** Attempted first with timeout handling
2. **Secondary (OpenAI-Compatible):** Attempted if primary fails, with separate timeout
3. **Tertiary (Offline):** Deterministic rule-based fallback requiring no external API

**Failure Recording:** Each provider failure is recorded by the `ProviderManager` to inform future selection decisions.

**45-Second Deadline:** An overall deadline prevents runaway chat turns from blocking the user interface. If the deadline is reached, remaining providers are skipped and the offline fallback is invoked.

## 20.2 Structured Error Responses

All API errors follow a consistent structure:

```json
{
  "detail": "Human-readable error message"
}
```

Common HTTP status codes used:
- `400 Bad Request` — Invalid request data
- `401 Unauthorized` — Missing or invalid JWT token
- `404 Not Found` — Resource not found
- `422 Unprocessable Entity` — Pydantic validation failure
- `429 Too Many Requests` — Rate limit exceeded

## 20.3 Database Error Handling

- **Connection failures:** The async engine automatically retries connections on transient failures
- **Transaction management:** All database operations use proper transaction scoping with `async with` sessions
- **Data integrity:** Foreign key constraints and unique indexes prevent inconsistent data states
- **Migration safety:** Alembic migrations ensure schema changes are applied atomically

## 20.4 Model Loading Resilience

The ML predictor service handles missing model artifacts gracefully:

```python
for domain, filename in [("finance", "finance_v1.joblib"), ...]:
    model_path = MODELS_DIR / filename
    if model_path.exists():
        try:
            self._models[domain] = joblib.load(model_path)
        except Exception as e:
            logger.error(f"Failed to load {model_path}: {e}")
    else:
        logger.warning(f"Model artifact not found: {model_path}")
```

If a model fails to load, the service falls back to heuristic default values rather than crashing.

## 20.5 Frontend Error Handling

- **API errors:** Displayed as toast notifications with actionable messages
- **Form validation:** Inline error messages for invalid input before submission
- **Network failures:** Retry prompts for transient network issues
- **Authentication expiry:** Automatic redirect to login page when JWT expires

## 20.6 Logging

The backend uses Python's standard `logging` module with structured log levels:
- `INFO` — Model loading, provider selection, successful operations
- `WARNING` — Fallback activations, missing models, non-critical errors
- `ERROR` — Model inference failures, provider crashes, database errors

# Chapter 22 — Implementation Highlights

## 22.1 Vectorized Monte Carlo Execution

The simulation engine achieves sub-100ms execution for 15,000 iterations by using fully vectorized NumPy operations instead of Python loops. All shock arrays are pre-allocated as `(iterations, horizon)` matrices, and cross-domain coupling is applied via element-wise NumPy operations:

```python
# Vectorized financial stress penalty (no Python loop over iterations)
b_fin_stress_penalty = np.where(
    b_runway < RUNWAY_MONTHS_STRESS_THRESHOLD,
    FINANCIAL_STRESS_HABIT_PENALTY * (1.0 - (b_runway / RUNWAY_MONTHS_STRESS_THRESHOLD)),
    0.0,
)
```

**Performance achieved:** 15,000 iterations in 0.08s (parametric), 0.09s (bootstrap), 0.15s (compare mode).

## 22.2 Cold-Start Dynamic Blending with Data Provenance

The system solves the cold-start problem through a smooth blending function:

```python
personal_weight = min(1.0, user_data_points / 30.0)
blended = (1.0 - personal_weight) * global_prediction + personal_weight * personal_prediction
```

Each response includes a human-readable `data_source` badge ("global", "blended", "personal") and a natural language `explanation` describing the exact blending methodology. This is a notable implementation of **explainable AI** principles.

## 22.3 Anti-Spoofing Context Injection

The AI chatbot's security architecture prevents the LLM from manipulating user identity:

```python
# tools.py - NO tool accepts user_id
# tool_executor.py - user_id injected from verified JWT
t_result = await execute_tool_call(
    tool_name=t_name,
    raw_args=t_args,  # LLM provides only tool-specific params
    db=db,
    user=user,  # Injected from JWT, NOT from LLM output
)
```

This ensures row-level tenant isolation even when the AI model generates tool call arguments.

## 22.4 Intelligent Chart Reconciliation

The `reconcile_charts_for_question` method in `ChatService` ensures visualization relevance:

```python
# Rule: Never attach expense donut to unrelated answers
if not is_spending:
    for r in records:
        if isinstance(r.result, dict) and r.result.get("chart_spec"):
            if r.result["chart_spec"].get("type") == "expense_donut":
                r.result["chart_spec"] = None  # Strip irrelevant chart
```

This prevents visual noise and ensures the user sees a chart that matches their question intent.

## 22.5 Cross-Platform UUID Compatibility

The custom `GUID` TypeDecorator enables seamless UUID handling across PostgreSQL and SQLite:

```python
class GUID(TypeDecorator):
    impl = CHAR(36)
    cache_ok = True

    def process_bind_param(self, value, dialect):
        return str(value) if value else value

    def process_result_value(self, value, dialect):
        return uuid.UUID(value) if value and not isinstance(value, uuid.UUID) else value
```

This eliminates the need for separate model definitions per database backend.

## 22.6 Multi-Provider LLM Resilience

The provider manager implements a circuit breaker pattern where failed providers are temporarily skipped:

```python
for p_name, provider in candidates:
    try:
        # ... execute chat turn with provider
        self.provider_manager.record_success(p_name)
        break
    except Exception:
        self.provider_manager.record_failure(p_name)
        continue
```

The system degrades gracefully from Gemini → OpenAI-Compatible → Offline, ensuring 100% availability.

## 30.4 Thread-Safe Rate Limiter (Security)

**File:** [`backend/app/core/security.py`](file:///d:/AI-Based-Virtual-Risk-and-Compliance/backend/app/core/security.py), Lines 61–79

```python
class InMemoryRateLimiter:
    def __init__(self):
        self._lock = threading.Lock()
        self._requests: Dict[str, list] = defaultdict(list)

    def is_allowed(self, key: str, max_requests: int, window_seconds: int = 60):
        now = time.time()
        cutoff = now - window_seconds
        with self._lock:
            timestamps = [t for t in self._requests[key] if t > cutoff]
            if len(timestamps) >= max_requests:
                retry_after = int(timestamps[0] + window_seconds - now) + 1
                self._requests[key] = timestamps
                return False, max(1, retry_after)
            timestamps.append(now)
            self._requests[key] = timestamps
            return True, 0
```

**Significance:** This implements a sliding window rate limiter that is thread-safe via `threading.Lock`, automatically purges expired timestamps, and computes the exact `Retry-After` duration for rate-limited clients.
